# 02. 비유로 이해하기

> 이 문서는 **개념을 잡기 위한 비유**만 모아 둔 곳입니다. 정확한 규칙과 파일 경로는 [04-판별 로직](04-판별-로직.md)을 보세요.
> 비유는 이해를 돕지만 어디까지나 비유입니다. 각 절 끝의 「비유가 깨지는 곳」을 꼭 같이 읽으세요.

## 1. Mono와 IL2CPP — 통역사냐, 완역본이냐

Unity 개발자는 C#으로 게임을 씁니다. 하지만 컴퓨터의 CPU는 C#을 모릅니다. 그 사이를 잇는 방법이 두 가지고, 이 도구가 판별하는 게 바로 그 둘입니다.

### 무대 설정

- **C# 소스 코드** = 작가가 한국어로 쓴 **원고**
- **IL (중간 언어)** = 그 원고를 기계가 읽기 좋은 **중립 언어로 옮긴 번역본**. Unity는 어느 쪽 백엔드를 쓰든 일단 여기까지는 똑같이 옵니다.
- **CPU** = 자기 나라 말(기계어)밖에 못 알아듣는 **관객**

### Mono = 통역사를 데리고 다닌다

공연장에 **중립 언어 번역본**을 그대로 들고 갑니다. 대신 **통역사를 한 명 고용해서 같이 데려갑니다.** 공연 중에 통역사가 실시간으로 관객의 언어로 옮겨 줍니다.

| 비유 | 실제 |
|---|---|
| 중립 언어 번역본 (그대로 존재) | `Assembly-CSharp.dll` — IL이 담긴 .NET 어셈블리 |
| 실시간 통역사 | Mono 런타임 (IL을 실행 직전에 기계어로 JIT 컴파일) |
| 통역사 대기실 | `MonoBleedingEdge\` 폴더 (또는 구버전은 `<게임>_Data\Mono\`) |
| 번역본을 모아 둔 서류함 | `<게임>_Data\Managed\` 폴더 |

**결과:** 원고에 해당하는 번역본이 게임 폴더에 **읽을 수 있는 상태로 그대로 남아 있습니다.** 아무나 꺼내서 읽을 수 있고, 심지어 **고쳐서 다시 넣을 수도** 있습니다. 이게 Mono 게임 모딩이 쉬운 이유의 전부입니다.

### IL2CPP = 미리 완역해서 인쇄하고, 원고는 파쇄한다

공연 전에 **번역본을 관객의 언어로 완전히 옮겨서 책으로 인쇄**해 둡니다. 통역사는 필요 없습니다. 그리고 **원본 번역본은 파쇄합니다.**

| 비유 | 실제 |
|---|---|
| 완역해서 인쇄한 책 | `GameAssembly.dll` — 네이티브 기계어 |
| 파쇄된 원고 | `Managed\*.dll`이 **없음** |
| 책 뒤에 남긴 색인(찾아보기) | `<게임>_Data\il2cpp_data\Metadata\global-metadata.dat` |
| 완역 작업을 한 번역기 | IL2CPP 변환기 (C# → IL → C++ → 네이티브) |

**결과:** 실행은 더 빠릅니다(공연 중 통역 대기 시간이 없으니까). 하지만 내용을 고치려면 **인쇄된 책의 활자를 직접 파야** 합니다.

### 왜 색인(`global-metadata.dat`)이 남아 있나

완역해서 인쇄하면 "이 문장이 원래 어느 챕터의 몇 번째 문단이었는지"를 알 수 없게 됩니다. 그런데 게임은 실행 중에 그걸 알아야 할 때가 있습니다 — 예를 들어 "이 오브젝트에 붙은 스크립트 이름이 `PlayerController`인가?"를 물어보는 코드가 있으면요.

그래서 IL2CPP는 **이름표와 구조 정보만 따로 떼어 색인 파일로 남깁니다.** 그게 `global-metadata.dat`입니다.

그리고 이 색인이 있기 때문에, 리버서는 인쇄된 책과 색인을 대조해서 **원고의 목차를 상당 부분 복원**할 수 있습니다. `Il2CppDumper` 같은 도구가 하는 일이 정확히 이겁니다. 완전한 원고 복원은 아니고, **"몇 페이지에 무슨 제목의 글이 있다"는 목차 수준**입니다.

### 비유가 깨지는 곳

- **통역사 = 느림**은 과장입니다. Mono의 JIT는 한 번 통역한 문장을 캐시해 둡니다. 실제 성능 차이는 게임마다 다르고, IL2CPP가 항상 압도적으로 빠른 것도 아닙니다.
- **한 공연에 통역사와 완역본이 동시에** 있을 수 있습니다. 런처는 Mono, 본편은 IL2CPP인 게임이 실제로 존재합니다. 그래서 이 도구는 두 태그를 **동시에** 붙일 수 있게 만들어져 있습니다 ([04-판별 로직](04-판별-로직.md) 참고).
- **파쇄가 완벽하지 않습니다.** IL2CPP 빌드에도 `Managed` 폴더가 남아 있는 경우가 드물게 있습니다. 그래서 이 도구는 `Managed` 폴더 하나만으로 Mono라고 단정하지 않습니다.

## 2. 스캐너 = 서가를 도는 사서

이 도구가 하는 일은 도서관 사서의 재고 조사와 같습니다.

| 비유 | 실제 |
|---|---|
| 도서관 건물들 | Steam 라이브러리 폴더들 (`C:\Program Files (x86)\Steam`, `H:\SteamLibrary`, …) |
| 각 건물의 열람실 | `steamapps\common` |
| 서가에 꽂힌 책 한 권 | 게임 폴더 하나 |
| 책을 펼쳐 판권면을 확인 | 게임 폴더 안에서 Unity 흔적을 찾기 |
| 책등에 붙이는 색 스티커 | 화면에 표시되는 태그 배지 |
| "파란 스티커만 보여 주세요" | 필터 콤보박스 |
| 조사 결과를 인쇄 | TXT로 내보내기 |

사서는 **책을 읽지 않습니다.** 판권면 몇 줄만 확인하고 스티커를 붙입니다. 이 도구도 마찬가지로 게임의 코드를 실행하거나 분석하지 않고, **특정 파일과 폴더가 있는지 없는지만** 봅니다.

### 비유가 깨지는 곳

예전에는 이 사서가 판권면만 보는 게 아니라 **책을 첫 장부터 끝 장까지 넘겨 보고 있었습니다.** 게임 폴더 전체를 깊이 제한 없이 순회했기 때문입니다. 백과사전 한 질짜리 게임(수십만 파일)에서 스캔이 느린 주된 이유였습니다.

지금은 **앞쪽 몇 장만 확인하고, 필요한 걸 다 찾으면 책을 덮습니다.** 그리고 사서가 한 명이 아니라 **여러 명이 서가를 나눠 맡습니다.** 실제 라이브러리(게임 885개) 기준 137초에서 0.7초로 줄었습니다 ([07-개선 로드맵](07-개선-로드맵.md) 1번). 단, 이건 사서가 서가를 한 번 돌아 본 뒤(디스크 캐시가 찬 상태) 다시 돈 시간입니다. 컴퓨터를 켜고 처음 도는 스캔은 훨씬 오래 걸릴 수 있습니다([06-빌드와 실행](06-빌드와-실행.md)).

## 3. Steam 라이브러리 찾기 = 체인점 본사에 물어보기

Steam 게임은 한 곳에만 설치되지 않습니다. C드라이브가 꽉 차서 H드라이브에 라이브러리를 하나 더 만드는 건 흔한 일입니다. 그럼 이 도구는 그 H드라이브를 어떻게 알까요?

**체인점 지점을 모두 찾는 방법**과 같습니다.

1. **본사 주소를 전화번호부에서 찾는다** → Windows 레지스트리에서 Steam 설치 경로를 읽습니다.
   `HKCU\Software\Valve\Steam` → `SteamPath`
2. **전화번호부에 없더라도 흔한 주소는 찍어 본다** → 드라이브마다 `Program Files (x86)\Steam`, `Steam`, `SteamLibrary` 같은 흔한 설치 위치를 확인합니다.
3. **본사에 가서 지점 목록을 받아 온다** → 찾은 곳마다 `steamapps\libraryfolders.vdf` 파일을 읽습니다. 여기에 모든 라이브러리 경로가 적혀 있습니다. 새로 알게 된 지점의 목록도 이어서 받아 옵니다.
4. **각 지점의 창고를 확인한다** → 각 라이브러리의 `steamapps\common` 폴더가 실제로 있는지 확인합니다.
5. **체인점이 아닌 개인 가게도 둘러본다** → 드라이브 최상위 폴더 중 Unity 게임 폴더처럼 생긴 것(실행 파일 + `*_Data` 등)을 따로 챙깁니다. Steam 밖에 복사해 둔 게임을 위한 것입니다.

예전에는 2번 자리에 개인 PC 경로(`H:\steam`, `H:\SteamLibrary`)가 하드코딩되어 있었습니다. 남의 동네 주소를 들고 다니며 "여기 지점 있나?" 하고 두드려 보는 셈이었죠. 지금은 특정 PC의 주소 대신 **누구에게나 흔한 주소 모양**을 모든 드라이브에서 찍어 봅니다([05-코드 레퍼런스](05-코드-레퍼런스.md)「`SteamLibraries.cs`」).

## 4. `<게임>_Data` 폴더 = 게임의 짐가방

Unity로 만든 게임을 빌드하면 항상 이 짝이 나옵니다.

```
Hollow Knight/
├─ hollow_knight.exe          ← 여행자 본인
├─ hollow_knight_Data/        ← 그 사람의 짐가방  (이름 = exe 이름 + "_Data")
│  ├─ Managed/                ←   서류철 (Mono일 때만)
│  ├─ il2cpp_data/            ←   색인집 (IL2CPP일 때만)
│  └─ ...                     ←   에셋, 텍스처, 사운드
├─ UnityPlayer.dll            ← 엔진 본체 (어느 쪽이든 있음)
└─ MonoBleedingEdge/          ← 통역사 대기실 (Mono일 때)
```

**핵심은 짐가방 이름이 `_Data`로 끝난다는 규칙**입니다. 이 도구는 이 규칙 하나에 기대어 "여기가 Unity 게임의 본거지구나"를 알아냅니다. 짐가방을 찾으면 그 **옆에 뭐가 놓여 있는지**(통역사 대기실? 완역본?)를 보고 백엔드를 판정합니다.

게임 폴더 안에 짐가방이 여러 개일 수 있습니다 — 런처 하나, 본편 하나. 그래서 이 도구는 **찾은 짐가방을 전부 검사**하고, 배지에는 나온 결과를 모두 붙입니다.

다만 목록을 나눌 때(「Unity Mono」 보기에 넣을지, 「Unity IL2CPP」 보기에 넣을지)는 **주인 짐가방 하나**를 고릅니다. 게임 폴더 이름과 짐가방 이름이 맞는지, 옆에 여행자(실행 파일)가 서 있는지를 차례로 따지고, 그래도 못 고르면 가장 큰 짐가방을 고릅니다. 크기로 고른 경우는 "확실하지 않음"으로 표시해 둡니다([04-판별 로직](04-판별-로직.md)「대표 플레이어 고르기」).

## 5. 태그 다섯 개 = 확신의 등급이 다른 다섯 개의 스티커

화면에 붙는 배지 다섯 개는 **신뢰도가 서로 다릅니다.** 같은 급으로 읽으면 안 됩니다.

| 배지 | 색 | 비유 | 확신도 |
|---|---|---|---|
| **Unity Mono** | 파랑 | 통역사와 원고를 둘 다 확인함 | **높음** — 이게 결론입니다 |
| **Unity IL2CPP** | 주황 | 완역본과 색인을 둘 다 확인함 | **높음** — 이게 결론입니다 |
| **MonoBleedingEdge** | 보라 | 통역사 대기실만 봄 | 중간 — 근거 자료 |
| **Managed** | 파랑 | 서류철이 있다는 것만 봄 | 낮음 — 근거 자료 |
| **중첩** | 초록 | 상자 안에 같은 이름 상자가 또 있음 | Unity와 무관 — 별개 관찰 |

앞의 둘은 **판정 결과**, 뒤의 셋은 **판정에 쓰인 재료거나 그냥 참고 정보**입니다. `MonoBleedingEdge`와 `Managed` 배지는 "왜 Mono라고 판정했는지"를 눈으로 확인하는 용도로 보면 됩니다.

**중첩** 태그만 성격이 완전히 다릅니다. `Foo\Foo\` 처럼 폴더 안에 같은 이름의 폴더가 한 겹 더 있는 경우인데, 일부 게임이 실제로 이렇게 배포되기 때문에 스캔 결과를 해석할 때 알아 두면 유용해서 남겨 둔 관찰 항목입니다.

> 보기 목록의 「중첩 (Unity 게임)」은 이 스티커와 기준이 다릅니다. 보기는 "상자 안쪽에 짐가방이 들어 있는가"(하위 폴더에 Unity 플레이어가 있는가)를 봅니다. 그래서 스티커는 붙었는데 보기에는 없는 게임, 그 반대인 게임이 모두 있습니다([10-이름과 내보내기](10-이름과-내보내기.md)「중첩 신호 두 가지」).

## 6. `[Flags]` 열거형 = 스티커는 겹쳐 붙일 수 있다

코드에서 백엔드는 이렇게 생겼습니다.

```csharp
[Flags]
public enum UnityBackend { Unknown = 0, Mono = 1, Il2Cpp = 2 }
```

이건 **"Mono냐 IL2CPP냐" 하는 라디오 버튼이 아니라, 체크박스 두 개**라는 뜻입니다.

| 값 | 의미 |
|---|---|
| `Unknown` | 스티커 없음 — Unity 흔적을 못 찾음 |
| `Mono` | 파란 스티커만 |
| `Il2Cpp` | 주황 스티커만 |
| `Mono \| Il2Cpp` | **둘 다** — 한 폴더에 백엔드가 다른 실행 파일이 공존 |

마지막 경우가 실제로 있기 때문에 이렇게 설계했습니다. 예를 들어 Mono로 만든 런처가 IL2CPP 본편을 띄우는 구조라면, 폴더 하나에 짐가방이 둘이고 성격이 서로 다릅니다. "둘 중 하나만 골라야 한다"고 만들었다면 이런 게임에서 무조건 틀린 답을 내놓게 됩니다.

### 비유가 깨지는 곳

스티커(배지)는 겹쳐 붙지만, **목록 칸은 하나만** 고릅니다. 보기 「Unity Mono」와 「Unity IL2CPP」는 위 4절의 주인 짐가방 기준이라서, 한 게임이 두 보기에 함께 나오지는 않습니다. 두 스티커가 다 붙은 게임은 주인 짐가방 쪽 보기에만 나옵니다.

## 7. 비유 → 실제 대조표 (요약)

| 비유 | 실제 |
|---|---|
| 작가의 원고 | C# 소스 코드 (배포본엔 없음) |
| 중립 언어 번역본 | IL — `.dll` 안의 중간 언어 |
| 실시간 통역사 | Mono 런타임 (JIT) |
| 통역사 대기실 | `MonoBleedingEdge\`, `<게임>_Data\Mono\` |
| 번역본 서류함 | `<게임>_Data\Managed\` |
| 대표 서류 | `Assembly-CSharp.dll`, `UnityEngine.dll` |
| 인쇄된 완역본 | `GameAssembly.dll` |
| 책 뒤 색인 | `<게임>_Data\il2cpp_data\Metadata\global-metadata.dat` |
| 무대 장치 일체 | `UnityPlayer.dll` (양쪽 공통) |
| 여행자의 짐가방 | `<게임>_Data\` |
| 도서관 건물 | Steam 라이브러리 |
| 열람실 | `steamapps\common` |
| 본사 주소 | 레지스트리 `HKCU\Software\Valve\Steam` |
| 지점 목록 | `steamapps\libraryfolders.vdf` |
| 사서의 색 스티커 | 태그 배지 |
